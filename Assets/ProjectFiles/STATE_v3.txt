Current project state


CORE ARCHITECTURE

GameState system implemented

- Persistent Bootstrap scene
- GameStateController singleton (DontDestroyOnLoad)
- Centralized scene transitions
- SceneNames constants (no magic strings)
- Scene self-registration (MainMenu, Lobby, Gameplay)
- UI communicates only with GameStateController

Scene flow

Boot -> MainMenu -> Lobby -> LoadingGame -> Gameplay

Scene loading mode

- Single scene loading
- Multiplayer scene transitions use NetworkManager.SceneManager.LoadScene(..., LoadSceneMode.Single)
- Clients do not manually load scenes during active network sessions
- Host/server is authoritative for scene transitions

Network topology

LOBBY SYSTEM

Lobby creation and joining handled by

RelayLobbyNetwork

Host flow

HostAsync()
- Create Relay allocation
- Generate Relay Join Code
- Generate short 6-digit Join Code
- Create Lobby
- Store Join Code in Lobby data
- Configure Unity Transport
- StartHost()

Client flow

JoinAsync(lobbyId)
- Join Lobby
- Read Relay Join Code from Lobby data
- Join Relay allocation
- Configure Unity Transport
- StartClient()

Client alternate flow

JoinByShortCodeAsync(shortCode)
- Query public lobbies
- Match short join code
- Join matching lobby
- Continue normal client flow

Lobby data

- relayJoinCode
- shortJoinCode

Lobby capacity

- Up to 8 players

LOBBY SLOT SYSTEM

Lobby slot management handled by

LobbySlotManager

Responsibilities

- Maintain player-to-slot assignments
- Keep team assignments stable for the session
- Synchronize slot UI across host and clients
- Provide team lookup for gameplay spawn/role assignment

Slot layout

- Team 1 = slots 0-3
- Team 2 = slots 4-7

Assignment order

- 0, 4, 1, 5, 2, 6, 3, 7

Meaning

- Players are assigned alternately between Team 1 and Team 2
- Team assignments persist and do not reshuffle during refresh

Networking behavior

- LobbySlotManager is a NetworkBehaviour
- Persistent across scenes via DontDestroyOnLoad
- Spawned on server and synchronized to clients
- Clients request slot refresh after network spawn
- Server is authoritative for slot assignment

Lobby slot UI elements handled by

LobbySlot

Displays

- Empty / occupied state
- Player name
- Host indicator

NETWORK PLAYER PREFAB

Prefab

Prefabs/Network/NetworkPlayer

Hierarchy

- NetworkPlayer (root NetworkObject)
  - PlayerCapsule
  - CameraRoot
    - MainCamera

Important prefab setup

- PlayerCapsule local position = (0, 1, 0)
- CharacterController remains on PlayerCapsule
- Network root is the authoritative object for spawn/teleport

Components

Root object
- NetworkObject
- NetworkTransform
- NetworkPlayerOwnership
- PlayerRole

Child object
- CharacterController
- PlayerMovement / Starter Assets controller
- KnockbackReceiver
- KnockbackMovementAdapter
- RespawnOnFall
- TargetedPushAbility

Authority model

- Owner-authoritative movement

Ownership handling

Handled by

NetworkPlayerOwnership

Responsibilities

If IsOwner
- Enable Camera
- Enable AudioListener
- Enable PlayerInput
- Update camera culling mask for Runner and Sabotager layers

If not owner
- Disable Camera
- Disable AudioListener
- Disable PlayerInput

Additional behavior

- Owner spawn position is synchronized with ClientRpc because owner clients do not receive initial transform state from NetworkTransform the same way as remote observers

GAMEPLAY ROLES

Two player roles

- Runner
- Sabotager

Gameplay design

Runners
- Navigate elevated obstacle course
- Respawn on fall

Sabotagers
- Stay on ground
- Use abilities to disrupt runners

Handled by

PlayerRole

Responsibilities

- Store current role in NetworkVariable<PlayerRoleType>
- Enable/disable role-specific components
- Apply Runner / Sabotager layer to full player hierarchy
- Refresh owner camera visibility after role changes

Role behavior

Runner
- RespawnOnFall enabled
- TargetedPushAbility disabled
- Layer set to Runner

Sabotager
- RespawnOnFall disabled
- TargetedPushAbility enabled
- Layer set to Sabotager

Role assignment authority

- Server only
- Set via PlayerRole.SetRoleServer(...)



GAMEPLAY SPAWN SYSTEM

Gameplay bootstrap handled by

NetworkGameManager

Responsibilities

- Wait for Netcode scene load completion event
- Spawn one NetworkPlayer per connected client
- Assign role based on LobbySlotManager team mapping
- Choose spawn point by role
- Assign respawn spawn point for runners
- Synchronize owner spawn position

Critical behavior

- Players are not spawned on a one-frame delay anymore
- Server waits for NetworkManager.SceneManager.OnLoadEventCompleted
- Only clients confirmed as finished loading Gameplay are spawned

Role mapping

- Team 1 -> Runner
- Team 2 -> Sabotager

Spawn groups

- RunnerSpawnPoints[]
- SabotagerSpawnPoints[]

Result

- Host and client both receive their NetworkPlayer correctly
- Client-owned camera is present after Gameplay load
- No client-side missing player/camera race condition remains



KNOCKBACK SYSTEM

Sabotager ability

TargetedPushAbility

Mechanics

- Targeted push / knockback interaction against runners

Runner receives knockback via

- KnockbackReceiver
- KnockbackMovementAdapter

Knockback integrates with CharacterController movement.



RESPAWN SYSTEM

Runner fall detection handled by

RespawnOnFall

Mechanics

- Checks root player world Y against killY
- On fall, teleports network root to assigned spawn point
- Restores PlayerCapsule local offset after teleport
- CharacterController temporarily disabled during teleport

Authority

- Only owning client performs respawn check for its own player

Spawn point assignment

- Set by NetworkGameManager at spawn time for runners
