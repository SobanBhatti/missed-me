STATE_v4

Current project state

END GOAL
Multiplayer minigame playlist platform (similar to GTA V's Playlist system):
- Host selects game modes from available minigames to create custom playlists
- Each game mode has its own scene
- Each game mode can have multiple turns/matches within a round
- Players progress through the playlist, accumulating scores across all minigames
- RunnerSabotager is one of many game modes in the collection


CORE ARCHITECTURE

GameState system implemented

- Persistent Bootstrap scene
- GameStateController singleton (DontDestroyOnLoad)
- Centralized scene transitions
- SceneNames constants (no magic strings)
- Scene self-registration (MainMenu, Lobby, Gameplay)
- UI communicates only with GameStateController

Scene flow

Boot -> MainMenu -> Lobby -> LoadingGame -> Gameplay (via MatchSessionManager)

Scene loading mode

- Single scene loading
- Multiplayer scene transitions use NetworkManager.SceneManager.LoadScene(..., LoadSceneMode.Single)
- Clients do not manually load scenes during active network sessions
- Host/server is authoritative for scene transitions

MATCH SESSION SYSTEM

Match session management handled by

MatchSessionManager

Location

- Bootstrap scene (DontDestroyOnLoad)
- NetworkBehaviour singleton

Responsibilities

- Maintain playlist of minigames (scene + game mode)
- Track current round index
- Initialize and track player scores across all minigames
- Load next minigame from playlist
- End match when playlist completes
- Support multiple turns/matches per game mode

Playlist System

- Currently: Serialized list of PlaylistEntry in inspector
- Each entry contains sceneName (string) and gameMode (GameModeType)
- Each entry represents one minigame in the playlist
- Server-authoritative round progression
- Automatic scene loading via NetworkManager.SceneManager
- Scores accumulate across all minigames in playlist

Playlist Customization (Planned - Critical Feature)

- Host can cherry-pick game modes in lobby before match starts
- Available game modes: RunnerSabotager, Race, Minigame, Puzzle, etc.
- Each game mode can be added multiple times to playlist
- Playlist configuration should be synced to all clients
- Playlist persists for entire match session

Round Progression Flow

StartMatch()
- Called by LobbyUI when host clicks Start Match
- Resets currentRoundIndex to -1
- Initializes player scores (all clients start at 0)
- Calls LoadNextRound()

LoadNextRound()
- Increments currentRoundIndex
- Checks if playlist exhausted -> EndMatch()
- Loads scene from current playlist entry
- Uses NetworkManager.SceneManager.LoadScene() for multiplayer sync
- Each game mode can have multiple turns/matches before advancing

EndMatch()
- Called when playlist is complete
- Currently logs match finished
- Future: will load results scene showing cumulative scores

Integration Points

- LobbyUI.OnStartMatchClicked() -> MatchSessionManager.StartMatch()
- RoundEndTrigger.EndRound() -> MatchSessionManager.LoadNextRound()
- GameModeManagers can trigger round end when conditions met (e.g., RunnerRoundTracker)

Game Mode Types

- RunnerSabotager (asymmetrical obstacle course)
- Race (competitive racing)
- Minigame (various small games)
- Puzzle (puzzle-solving challenges)
- Additional game modes can be added

Game Mode Architecture

- Each game mode has its own scene
- Each game mode has its own GameModeManager implementation
- Game modes are independent and can be mixed in playlists
- Each game mode can support multiple turns/matches per round

Scripts

SPAWN POINT SYSTEM

Spawn point component system implemented

SpawnPoint Component

Scripts

- SpawnPoint
- SpawnPointType (enum)

Properties

- type: SpawnPointType
- index: int

SpawnPointType Enum

- Generic (fallback)
- RunnerStart
- SabotagerStart
- RaceStart
- Checkpoint (not yet used)

Spawn Point Discovery

- GameModeManager finds all SpawnPoint components on scene load
- Uses FindObjectsByType<SpawnPoint>()
- Stores in spawnPoints list

Spawn Point Assignment (RunnerSabotagerGameManager)

GetSpawnPoint(clientId) logic

1. Get role for client from LobbySlotManager
2. Determine SpawnPointType (RunnerStart or SabotagerStart)
3. Filter spawnPoints by type
4. Order by index
5. Find client's index within same-role clients
6. Return spawn at (roleIndex % candidates.Count)

Fixed Behavior

- SpawnPoints automatically discovered (no manual array assignment)
- Proper role-based assignment with index cycling
- Multiple spawns of same type supported via index
- Falls back to Generic spawn if role-specific not found
- Falls back to GameModeManager transform if no spawns found

Respawn Point Assignment

- RunnerSabotagerGameManager assigns respawn point from initial spawn
- RespawnOnFall.SetSpawnPoint() stores the spawn transform
- Respawn uses same location as initial spawn

RESPAWN SYSTEM

Runner fall detection handled by

RespawnOnFall

Mechanics

- Checks root player world Y against killY
- On fall, teleports network root to assigned spawn point
- Restores PlayerCapsule local offset after teleport
- CharacterController temporarily disabled during teleport

Authority

- Only owning client performs respawn check for its own player

Spawn point assignment

- Set by RunnerSabotagerGameManager at spawn time for runners
- Uses same spawn point as initial spawn


ROUND SYSTEM

Round progression handled by

MatchSessionManager

Round end triggers

RoundEndTrigger
- Manual trigger component
- Calls MatchSessionManager.LoadNextRound()

RunnerRoundTracker
- Tracks fallen runners
- Counts total runners at start
- When all runners fall, calls MatchSessionManager.LoadNextRound()

Round end flow

1. Trigger calls MatchSessionManager.LoadNextRound()
2. MatchSessionManager increments round index
3. Loads next scene from playlist
4. New scene's GameModeManager spawns players
5. Round begins
